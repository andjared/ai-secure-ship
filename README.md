# SecureShip

SecureShip is a shipment-support chat. Anyone can open it and talk to the assistant, but the assistant can reach a customer's shipment data only after the visitor has proven who they are: they give their first name, last name, address and phone number in the conversation, and then enter a 6-digit code. A separate admin panel, behind an Auth0 login, manages the customer, shipment and package records.

The chat runs on a local open-source model through Ollama. All customer data is synthetic, and the 6-digit code is mock 2FA: it is written to the backend log, not sent by SMS.

The product spec is [`REQUIREMENTS.md`](./REQUIREMENTS.md) and the week-by-week build plan is [`docs/DEV_PLAN.md`](./docs/DEV_PLAN.md).

## How it works

- **Identity gate.** Every chat session has a state, stored on the server: `anonymous → collecting_identity → code_sent → awaiting_code → verified`. Only backend code changes it. The model is asked to pull details out of the visitor's messages and to write replies; it never decides whether someone is verified. See [the state machine](docs/diagrams/identity-gating-state-machine.md).
- **Matching.** All four details must match the same single customer (ignoring case, extra spaces, address punctuation and phone formatting). On a miss the visitor gets one neutral message that does not say which detail was wrong or whether such a customer exists.
- **Code.** On a match the backend issues a 6-digit code, valid for 10 minutes and 3 attempts, and the chat opens a modal to enter it. Only a correct code makes the session `verified` and ties it to the customer.
- **One tool, one enforcement point.** A verified session's chat offers the model a single tool, `lookup_shipments`, which takes no parameters. Every call goes through `run_tool` in `backend/app/tools/lookup_shipments.py`, which refuses anything but a verified session and reads the customer only from the session, so nothing the model or the visitor says can widen the lookup. See [the tool-calling sequence](docs/diagrams/tool-calling-sequence-http.md).
- **Human escalation.** "I want to talk to a human" plays a scripted handoff to "Melany" and changes the window color. It is cosmetic: there is no human, and the gate underneath is unchanged. See [the escalation sequence](docs/diagrams/human-escalation-sequence.md).
- **Admin.** The admin panel at `/admin` creates, edits and deletes customers, shipments and packages. Every `/admin` API route requires a valid Auth0 access token. Admin login and the chat's identity gate share no code or state. See [the architecture](docs/diagrams/system-architecture.md) and [the separation checks](docs/admin-chat-separation.md).
- **Storage.** Each conversation is one row in `chat_sessions`, with its state and the full transcript as JSONB. See [the data model](docs/diagrams/data-model.md).

## Stack

- **Frontend:** React 19 + TypeScript (Vite), React Query, API client generated by Orval from the backend's OpenAPI schema
- **Backend:** FastAPI (Python 3.12) with SQLAlchemy 2.0
- **Database:** Postgres 16
- **Local LLM:** Ollama with `qwen3:8b`, running on the host (not in Docker — see [the deployment topology](docs/diagrams/deployment-topology.md))
- **Admin login:** Auth0 (admin area only)

The chat uses plain HTTP request/response; replies are not streamed.

## Prerequisites

- Docker with Docker Compose
- [Ollama](https://ollama.com/download) installed on the host, with the model pulled: `ollama pull qwen3:8b`
- An Auth0 tenant. The backend refuses to start without its Auth0 settings, even if you only want the chat; see [Admin login (Auth0)](#admin-login-auth0).
- Only for running without Docker: Node.js and Python 3.12

## Quick start (Docker)

1. Start Ollama on the host if it isn't already running:

   ```bash
   ollama serve
   ```

2. Create `backend/.env` and `frontend/.env` from their `.env.example` files, as described in [Admin login (Auth0)](#admin-login-auth0).

3. Start the frontend, backend and Postgres:

   ```bash
   docker compose up
   ```

4. Fill the database with mock customers, shipments and packages:

   ```bash
   docker compose exec backend python -m scripts.seed_data
   ```

   It's idempotent — safe to re-run, it clears and regenerates rather than accumulating duplicates. That also means it replaces any records you created or edited in the admin panel.

5. Open the app:
   - Chat: http://localhost:3000
   - Admin panel: http://localhost:3000/admin
   - Backend health check: http://localhost:8000/health
   - Postgres: localhost:5432

The backend reaches Ollama on the host at `host.docker.internal:11434`.

The backend image bakes in the code at build time (no volume mount, no auto-reload), so after changing backend code rebuild and restart it:

```bash
docker compose up -d --build backend
```

## Try it

The mock data is random, so first pick a customer to play:

```bash
docker compose exec postgres psql -U user -d secureship -c "select first_name, last_name, address, phone_number from customers limit 5;"
```

Then, in the chat at http://localhost:3000:

1. **Chat without verifying.** Ask a general question about shipping. The assistant answers and has no access to shipment data.
2. **Ask about a shipment**, for example "Where is my package?". The assistant asks for your first name, last name, address and phone number. Give them in one message or over several.
3. **Get the code.** Once all four details match your customer, the chat replies "Thanks, let me check those details." and opens the code modal. The code is in the backend log, on a line starting with `mock SMS to session`:

   ```bash
   docker compose logs backend | grep "mock SMS"
   ```

4. **Enter the code.** The chat confirms you are verified.
5. **Ask about your shipments**, for example "What's the status of my shipments?". The assistant answers from that customer's records and the chat shows a card per shipment.
6. **Ask for a human**: "I want to talk to a human". The scripted handoff plays. This works at any point and gives no extra access.
7. **Edit as an admin.** Open http://localhost:3000/admin in another tab, log in, and change the status of one of that customer's shipments. Ask the verified chat about your shipments again: it shows the new status.

Things to try on purpose:

- **A wrong detail.** Change one detail, for example the phone number. Once all four are given, the reply is "Sorry, we couldn't verify those details. Please double-check them and try again." whatever was wrong, and you start over.
- **A wrong code.** You get 3 attempts. After the third wrong code, or after 10 minutes, the code can no longer be used and you are asked to share your details again.
- **A new tab.** Verification belongs to the chat session, which the browser keeps per tab. A new tab is a new anonymous session.

## Running locally without Docker

Postgres can stay in Docker while the backend and frontend run natively — useful for live code reload.

### Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Keep Postgres running via Docker (from the repo root):

```bash
docker compose up -d postgres
```

Set env vars (these differ from the in-container values — `host.docker.internal` only resolves inside a container):

```bash
export DATABASE_URL=postgresql://user:pass@localhost:5432/secureship
export OLLAMA_HOST=http://localhost:11434
export AUTH0_DOMAIN=your-tenant.us.auth0.com      # see "Admin login (Auth0)"
export AUTH0_AUDIENCE=https://your-api-identifier
```

Then run with live reload:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Ollama must still be running on the host (`ollama serve`), same as the Docker path.

To seed the mock data natively, run this from `backend/` with the same env vars set:

```bash
python -m scripts.seed_data
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Serves on http://localhost:3000, same as the Docker path.

> Don't run both the Docker `backend`/`frontend` containers and the native processes at the same time — they'd conflict on ports 8000/3000.

## Admin login (Auth0)

The admin area lives at http://localhost:3000/admin and requires an Auth0 login. The chat at `/` does not use Auth0 at all.

One-time setup in the [Auth0 Dashboard](https://manage.auth0.com):

1. **Applications → Applications → Create Application**, type **Single Page Web Applications**. In its settings:
   - Allowed Callback URLs: `http://localhost:3000/admin`
   - Allowed Logout URLs: `http://localhost:3000/admin`
   - Allowed Web Origins: `http://localhost:3000`
2. **Applications → APIs → Create API**. Its identifier is the audience. Then open the API's **Application Access** tab and, under **User-Delegated Access**, grant access to the application from step 1; without this, login fails with "Client is not authorized to access resource server".
3. **Authentication → Database → Username-Password-Authentication**: turn on **Disable Sign Ups**, so nobody can register themselves as an admin.
4. **User Management → Users → Create User** for each admin.
5. In the application's **Connections** tab, switch off `google-oauth2`, so only the users you created can log in.

Then copy `frontend/.env.example` to `frontend/.env` and fill in the tenant domain, the application's client ID and the API identifier. Restart `npm run dev` afterwards; with Docker, rebuild the image instead (`docker compose up -d --build frontend`), since it copies `.env` at build time.

The backend validates the admin's access token on every `/admin` route, so it needs the same tenant domain and API identifier. Copy `backend/.env.example` to `backend/.env` and fill in `AUTH0_DOMAIN` (no `https://`) and `AUTH0_AUDIENCE`; Docker Compose passes that file to the backend container (`docker compose up -d backend` picks up changes). When running the backend natively, export the two values instead. The backend refuses to start without them, and a request to `/admin` without a valid token is rejected (`curl -i http://localhost:8000/admin/customers`).

Admin login and the chat's identity check are separate systems: an admin cannot become a verified chat session and a chat session cannot reach `/admin`. The checks are recorded in [docs/admin-chat-separation.md](docs/admin-chat-separation.md).

## Security notes

- **The gate is enforced on the server.** Session state and the linked customer are set only by backend code; the model and the frontend cannot set them.
- **Failure messages are neutral.** A failed identity check and an unusable code each have one fixed message, so they can't be used to find out which customers exist.
- **No personal details in logs.** Logs name the session and the outcome only. The verification code appears on the mock SMS line, as the stand-in for sending it.
- **Local model only.** The chat talks only to Ollama.

The checks behind these claims are written up in [docs/prompt-injection-tests.md](docs/prompt-injection-tests.md) (can a visitor reach another customer's shipments through the chat?) and [docs/admin-chat-separation.md](docs/admin-chat-separation.md).

## Regenerating the API client

The frontend's API types and React Query hooks in `frontend/src/api/generated/` are generated by Orval and are never edited by hand. After changing a backend route or its request/response models, regenerate them with the backend running on port 8000:

```bash
cd frontend
npm run generate-api
```

## Inspecting the database

Postgres runs in the `postgres` container regardless of whether the backend runs in Docker or natively. Connect to it with `psql` via `docker compose exec`:

```bash
# Interactive session
docker compose exec postgres psql -U user -d secureship
```

Once inside, a few useful commands:

```sql
\dt              -- list all tables
\d customers     -- show a table's columns and types
\q               -- quit
```

Or run one-off queries without opening an interactive session:

```bash
# List tables
docker compose exec postgres psql -U user -d secureship -c "\dt"

# Peek at some rows
docker compose exec postgres psql -U user -d secureship -c "select * from customers limit 5;"
docker compose exec postgres psql -U user -d secureship -c "select * from shipments limit 5;"

# Row counts
docker compose exec postgres psql -U user -d secureship -c "select count(*) from customers;"

# Shipment status distribution
docker compose exec postgres psql -U user -d secureship -c "select status, count(*) from shipments group by status;"

# A session's stored conversation transcript
docker compose exec postgres psql -U user -d secureship -c "select id, state, transcript from chat_sessions;"
```

Prefer a GUI? Point a client like TablePlus, DBeaver, or Postico at `localhost:5432`, database `secureship`, user `user`, password `pass` (from `docker-compose.yml`).

To (re)populate the `customers`/`shipments`/`packages` tables with mock data, run the seed script from [Quick start](#quick-start-docker).

## Known limitations

- Verification codes are kept in the backend's memory. Restarting the backend drops any code in flight (the visitor is asked for their details again), and the backend must run as a single process.
- There are no database migrations; tables are created on startup. After changing a column on an existing table, drop that table or the whole volume (`docker compose down -v`, which deletes all data).
- Chat sessions never expire or end, and a verified session stays verified.
- While a code is pending, the only way back to giving details is to submit a code; the chat itself keeps re-opening the modal.
- The `escalated_to_human` session state and the `ended_at` column exist but are not used.
- A request for a human is detected by keywords, not by the model.
- Each call to Ollama times out after 60 seconds. A slower reply fails and the chat shows "Something went wrong — please try again."
- The model name `qwen3:8b` is set in the code. Other models have not been tested.
- Not built: real SMS, a containerized Ollama, and an admin page for viewing chat sessions.
